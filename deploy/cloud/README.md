# 普通 DSH 会话的跨设备共享

共享属于「手机连接」桌面插件。直接在 DSH 原来的工作区新建或打开会话；不需要单独安装“共享任务”插件、打开浏览器或移动任务。手机连接电脑时看到的就是桌面 DSH；连接云端时使用同一个会话 ID 查找已同步的历史。手机的「新建会话」留在当前执行端。

在已经配对的两台主机上，给现有 `id: mobile-link` 的 `config` 加 `taskSync: {role: desktop, sshHost: your-verified-ssh-alias}`（电脑）或 `taskSync: {role: cloud}`（服务器）。没有这个配置的安装不会上传任何会话。将插件自带的 `desktop/lib/task-sync/transfer.py` 安装到云端 `/opt/dsh-cloud/task-transfer.py`。保留原 `mobile-link` 家庭配对配置和受信 SSH 主机密钥。升级旧部署时禁用旧 `shared-sessions` 配置；不要删除原工作区或历史文件。

* 两端读取已注册工作区，使用 DSH 自己的会话存储接口。即使没有会话，工作区也会出现在另一端。同步身份是创建端与原始工作区 ID 的组合：重命名不改变身份，同名项目也不会误合并。原工作区改名后，副本在下一次目录核对时更新名称。远端路径不会作为本机目录使用。
* 历史使用原始会话 ID、事件、工具结果、时间和分支元数据。已同步的完整轮次可以在另一台机器上打开。历史是任务数据，可能含聊天中粘贴的秘密或工具输出；只发给配对的私人服务器，不进入代码仓库。不会复制整个项目目录、模型凭据文件或附件文件库。
* 在一端正在执行或持有写锁时，不在另一端重放工具。只向原生会话追加经校验的完整轮次；未完成的进度保留在同步收件箱。两端历史分叉时保留双方记录，不强行覆盖。同步不是 Windows 进程迁移，电脑断电不会让本地命令自动在 Linux 接着运行。
* 工具调用、工具结果和步骤结束都会触发增量发布，不必等到轮次结束。电脑与云端通过同一条已校验主机密钥的 SSH 连接双向轮询，正常间隔 1.5 秒；每 12 秒仍做一次工作区全量核对。SSH 不通不会堵住本机记录，也不会阻止另一端读取已经送达的记录。这些间隔不是接管时限，更不是同步提交保证。
* 排队的输入有时出现在 `turn/start` 之前。它和没有结果的命令一样，只保留在检查点，不注入备用端的可执行队列。在结果未知时，不能仅根据心跳超时重跑命令；完成部署、扣款等操作后，执行端也可能来不及写回结果。
* 普通、置顶、归档是同一个会话的三种互斥状态。两端均可更改；逻辑版本保存在本机，重启或收到旧包不会把已同步的新操作撤销。归档仍服从 DSH 原生运行保护；删除会话或真实项目不会跨端传播。云端 DSH Web 服务仍只监听回环地址，不公开 owner 接口。

上游无法迁移的 v3 历史按原格式保留：只替换云端的工作目录头，后续压缩事件字节不变，不补造缺失的工具结果。桌面与云端会有相同的迁移限制。

### 云端跟随电脑的模型设置

在已启用上述配对同步的主机上，不必在云端再建一套模型列表。插件使用 DSH 原生设置接口，将电脑的自定义供应商、HTTPS Base URL、模型能力、默认模型和推理强度**单向**同步到云端；修改或移除配置、断线重连后也按电脑的设置核对。已有会话保留自己的模型选择，云端不会把自己的默认模型倒写到电脑。修改在服务端生效，不需要更换手机 App。

两端仍使用各自的凭据库。同步只包含 API Key 的引用名，不包含密钥值、登录令牌、Cookie 或自定义 HTTP 请求头。需要相应凭据的云端供应商必须先在该服务器上配置凭据。包含用户名、密码或查询参数的 Base URL 不参加同步；有私有请求头的云端供应商不会被自动移除或改绑到其他端点。云端离线时继续使用最后一次成功应用的设置。

在云端或电脑给工作区改名，改的都是原来同一个工作区。两台机器同时离线改名时按保存的逻辑版本合并，手机不会因此多出一行。没有「本地」或「云端」分组。

### 从旧版“来自……”分组迁移

先停用旧的独立共享插件。核对两端原生注册记录与 `mobile-task-sync/routes` 中的来源，记录旧分组的**创建端工作区 ID**，不要用展示名筛选或直接修改 `storages/workspace.json`。两端的 `DSH_HOME/mobile-task-sync/retired-workspaces.json` 使用同一份清单，例如：

```json
{"desktop":["old-desktop-workspace-id"],"cloud":["old-cloud-workspace-id"]}
```

这份清单仅存在于个人部署，不进公开仓库。插件按原始身份识别旧分组及其副本；只注销空项目或仅含初始权限设置的草稿，并保留目录和会话文件。若有已打开的会话、真实消息、工具记录或不可读历史，则保留注册，不自动迁走或合并。迟到的旧目录和旧会话包不会重新生成这些分组。

接力的验收条件是另一端能用原会话 ID 打开已落盘的轮次、生成下一轮，并把结果写回原工作区。跨主机的工作区路径不同；要在两端操作同一份工程文件，必须另外准备经授权的同步目录或仓库检出。不要把整块磁盘、个人配置目录或模型凭据当作要自动上传的工作区内容。

### 0.7.10：在原会话提交可离线的云端任务

在配对两端的 `taskSync` 配置中分别启用 `cloudTurns: true`。电脑端选择已有会话，在「手机连接 → 本会话云端执行」填写任务。无需另建工作区。这个入口提交**新的一轮**；不会抢占或重跑正在执行的本地命令。手机也可以直接在同一会话的云端设备上发送消息。模型密钥和工作目录内的实际文件需要预先在云端就绪，不会随任务自动上传。

电脑插件先保存原生会话与用户提交记录，再由已配对的 SSH 传输把这份委托交到云端。普通历史快照不会触发执行。云端核对会话前缀、归档状态和委托身份；有分叉不覆盖，有未释放的本机写入者不抢锁。云端在调度前持久化唯一领取记录，遇到结果不明的提交不自动重跑。未领取的委托在 15 分钟后失效。「本机登记」不等于「云端已开始」：如果原电脑可能立即完全断电，要以云端同一会话出现这一轮为准。首次从已打开且正在写入的云端会话向电脑反向接管，不在这个功能的保证范围内。

Windows 可在同一个 DSH 用户下运行插件内 `tools/windows-cloud-inbox.ps1 -SshHost <已校验主机密钥的 SSH 别名>`。独立的 Windows 计划任务在该用户登录后每分钟补投已登记的云端任务、接收云端结果；不会启动桌面 DSH。电脑断网时结果留在云端。恢复网络后，即使桌面程序未启动，收件箱也会落盘；下次打开 DSH 时才导入原会话。使用 `-Disable` 可移除计划任务，保留已收到的数据。若需 Windows **登录前**开始收件，可由管理员在相同用户身份下使用 `-BeforeSignIn`；须验证该账户在非交互会话能使用指定 SSH 身份。不要把用户密码、SSH 私钥或模型密钥写入脚本。

### 0.7.11：普通终端步骤的接力（Windows → Linux，不用虚拟机）

这不是远程终端，也不是把一个 Windows 进程恢复成 Linux 进程。在配对主机的 `taskSync` 中设置 `portableSteps: true` 后，标准模式会话内符合下表的前台 PowerShell / Bash 命令会自动登记，不需要先提交 `/cloud-run`。不支持持久终端、后台作业、提权、嵌套 PTC 调用、自定义工作目录和任意脚本。其他命令照原样在本机运行，不会自动在云端重放。

| 命令形式（示例） | 接力的工作 |
| --- | --- |
| `Start-Sleep -Seconds 5` / `sleep 5` | 用云端登记的到期时间，只等剩余时间 |
| `Write-Output '完成'` / `printf '%s\n' '完成'` | 产生指定文本；不执行文本内容 |
| `(Get-FileHash -LiteralPath 'relay-inputs/data.bin' -Algorithm SHA256).Hash` / `sha256sum -- 'relay-inputs/data.bin'` | 对登记时的文件内容重新计算 SHA-256 |
| `(Get-Item -LiteralPath 'relay-inputs/data.bin').Length` / `wc -c < 'relay-inputs/data.bin'` | 取得登记时的文件字节数 |

可以在后三类操作前加一段等待，例如 `Start-Sleep -Seconds 5; (Get-FileHash -LiteralPath 'relay-inputs/data.bin' -Algorithm SHA256).Hash`。登记文件必须是工作区根目录 `relay-inputs` 下的非链接普通文件，单文件不超过 1 MiB；不要把秘密放进去。**这是命令接力输入的限制，不是手机附件的大小限制。** 只有命令指定的那个文件会传输；插件不扫描或上传整个工程。若文件在登记后发生修改，云端使用登记时的版本。

云端把步骤和输入持久化后，本机才开始执行登记的命令。在发出登记前就发现备用端不通时，普通命令仍在本机运行，但没有断电保护。若发出登记后丢失确认，则不重复启动。如果命令已经在本机真实完成，备用端掉线不抹掉本机的真实结果。租约每 2.5 秒续一次，超过 10 秒未续就拒绝旧执行者提交；独立云端服务每秒检查到期步骤，不依赖桌面 DSH 或 SSH 连接存活。只读计算可以重复，但同一会话、同一调用只接纳一份最终回执。网络分区不能强行停掉另一端已有的进程。接力回执与 DSH 原生工具结果分开存储，不伪造对话、不自动对有副作用的命令补跑。

在原会话输入 `/relay-status` 查看最近十条回执；桌面关闭时已安装的 Windows 收件箱仍能下载回执，下次打开即可查看。云端完成一个终端步骤不等于自动跑完其余模型步骤。Windows 用户明确取消并成功送达云端的步骤不再接力；如果机器断网导致取消未送达，云端仍可能完成已登记的只读计算。

部署：在已配对的 DSH Linux 主机上，将本版本 `portable_worker.py` 和 `transfer.py` 分别安装到 `/opt/dsh-cloud/portable_worker.py`、`/opt/dsh-cloud/task-transfer.py`；将 `dsh-portable-steps.service` 安装为 systemd 服务并启用。需要已存在且归 `dsh-cloud` 所有的 `mobile-task-sync` 目录。服务以 `dsh-cloud` 用户运行，不开公网端口。桌面更新插件后重新注册随包的 Windows 收件箱，才能在桌面关闭时接收新格式的回执。旧版正常会话同步不依赖这个服务。

### 0.7.12：让另一台 DSH 接管后续模型轮次（双向）

两端更新插件和任务传输脚本，并分别在已配对主机的 `taskSync` 配置中打开 `turnRelay: true`。未开启的主机不注册接力工具，也不会因为同步了一段聊天记录而执行它。普通用户不需要另外创建云端工作区。

- `relay_environment` 只读：在执行端报告 OS、架构、当前工作目录、DSH 原生 Shell 工具、PATH 上发现及未发现的程序，以及项目根目录的依赖清单。不输出环境变量和密钥，也不把「发现 npm」当成「这个项目的依赖已安装」。
- `relay_remaining_task` 由模型在独立步骤里调用。接力包必须含真实的工具成功结果，以及同一步、同一轮的正常结束事件；有正在运行的后台作业、排队输入或同时发生的其他工具调用时不交接。接手端只在原会话、匹配的历史前缀及兼容的权限下提交固定的继续消息，之后由原生 DSH 调模型、执行工具和请求审批。不会将工具输出当作新的用户命令，也不会因为模型自己的接力提示来回切换。
- 若需要把少量工程文件随步骤一起交付，在**源设备** DSH 的 `mobile-task-sync/relay-inputs.json` 显式列出允许的输入。例如 `{"desktop:<原工作区 ID>":["package.json","build.cjs"]}`。配置文件在工作区外。0.7.12–0.7.16 仅支持根目录的普通文件（最多 32 个，合计 1 MiB）；两端升级到 0.7.17 后可列出子目录内的普通文件，见下文。不追随链接，不递归扫描。没有此配置时不传文件。接手端校验字节和 SHA-256，在受管工作区仅创建缺失文件，不覆盖不同版本；回到原工作区只校验，不写入。大型工程和原生依赖仍需分别准备。
- 已落盘的接力包可以通过后台收件箱转送；**尚未传到另一端时**突然断电，另一端不能凭空重建这个包。接手后原设备离线不影响接手端后续轮次，结果仍由普通会话同步带回。原生运行时还持有同一会话写入权或两端历史不同，不强行拼接历史。收到相同接力包不重复提交；执行确认丢失不自动重试有副作用的整轮任务。首轮领取有效期 24 小时。

**这是任务交接，不是搬运进程内存。** 跨平台验收使用两端隔离的 DSH 和可复现的模型响应：在源端生成交接包并关闭源 DSH，目标端从空的受管工作区接收两个获准的输入文件，调用环境工具、执行一次实际的 `npm run build`，再调用模型生成最终回复。这个测试不代表已经运行到一半的任意构建、安装、部署或任意脚本能在断电后从下一条 CPU 指令继续。不能确认外部写入是否成功时，先查询目标系统，不能盲目重放。

### iPhone 的公网云端入口

移动端在设备名下方列出同一配对中的电脑与云服务器。电脑 `mobile-link/family-route.json` 的可选 `displayName` 是给手机显示的设备名称（例如「阿里云 ECS · 广州」），不影响公钥、设备 ID 或授权。旧配置只返回「云端」时，手机用云服务器加设备 ID 短尾区分。

自签名证书配合 sslip.io 时，将云节点域名设为 `<以连字符分隔的 IPv4>.dsh-cloud.sslip.io`。在现有 TLS 透传入口为它配置与旧云域名相同的 SNI 后端，保留原域名，再修改电脑的 `endpoint`。先从公网验证新域名的叶证书 SPKI 和 `/mobile/v1/hello` 身份均与原授权一致。不要把流量送到桌面中继、公开云端 DSH 管理端口，或让客户端学习网络上第一次看到的公钥。其他自有域名可使用系统信任的有效证书和与授权一致的公钥；本 App 没有为整个 sslip.io 或所有公网域名放开 ATS。

### 0.7.14：接管后读取执行记录

接管端的 `relay_environment` 除了报告当前平台、工具和目录，还会从这个会话的原生日志读回最近一次接力的源端步骤：用户请求、工具调用及结果的事件序号，哪些工具报错、哪些缺少结果。最多返回最近 32 个工具调用，并报告省略数量；不额外复制命令参数、正文或凭据。仅被动同步来的历史不会被当成本机刚接管的任务。

如果接管端尚未提交新轮次就取消，保存在收件箱的任务可以重试。若提交后丢失确认，插件按原生请求 ID 核对同一会话的新收件或用户消息记录，不会再次派发同一任务。这个确认只表示 **DSH 收到了请求**，不表示部署或安装成功。没有可核对的记录时保留待查，不盲目重跑。这是步骤边界的接力，不是断电后迁移进程内存。

### 0.7.15：核对 Git 发布是否已经提交

这项功能面向**已明确接入的自管裸 Git 仓库**，解决「发布分支已更新，但发送端没收到回执」的问题。它不会修改现有仓库、托管平台的保护规则或 CI，也不把普通 `git push` 自动替换成发布。没有目标配合的部署，不能凭进程退出码断定成功或失败。

**一次性接入条件（由仓库管理员完成，不交给模型自行放宽权限）：**

- 服务端支持原子推送，并能运行 `reference-transaction` 钩子。在启用保护之前建立发布分支、创建仓库独有的身份对象，用 `refs/dsh-relay/identity` 固定其完整对象 ID。设置仓库本地 `dshRelay.protectedBranch` 为这个分支名。复制插件里的 `tools/relay-git-guard.mjs` 和它引用的 `lib/task-sync/git-release.mjs`，保留相对路径；让原有钩子在 `prepared` 阶段把**同一份完整标准输入**和阶段参数交给该守卫，任一检查失败均须拒绝事务。不要覆盖旧钩子。守卫启用后，直接改写发布分支、删除或重写接力回执、轮换仓库身份都会被拦截。先用新建的测试仓库验证，再由管理员决定是否接入正式分支。
- 两端均需有该仓库的 Git 客户端、已有的读写授权和单一指向同一仓库的读写 remote，并分别设置仓库本地 `dshRelay.<remote>.identity` 与 `dshRelay.<remote>.branch`。这不是系统级配置。CI 必须只监听正式发布分支，**不要监听** `refs/dsh-relay/` 下用于暂存对象和保留回执的内部引用。保留这些引用供设备掉线后核对，勿擅自清理。

**一次发布如何接力：** DSH 的 `relay_git_release_plan` 将目标身份、分支、原提交、期望提交和稳定操作编号写入原会话，不执行推送。两端通过原生 Shell 和已有审批调用 `relay_environment` 给出的当前主机脚本路径：

```text
node <脚本路径> <prepare|status|finish> <remote> <分支> <原操作编号> <仓库身份> <原提交> <期望提交>
```

`prepare` 只把计划和提交对象保存到目标仓库，不动发布分支。另一台机器即使没有原工作树，也可以用 `status` 查询原操作，`finish` 从已准备的目标取回对象，再原子地更新分支和创建不可覆盖的回执。只允许从预期版本向前更新；已有匹配回执则只读返回，哪怕分支已推进到更高版本。目标不可达、分支被其他操作更改、身份或回执不符时，不以重新推送试探结果。`committed` 只证明 Git 引用事务提交了，**不证明下游应用已部署成功**。后者必须另外核对发布平台的运行记录。

用于验收时，可将 `deploy/cloud/create-release-sandbox.py <全新目录> <已安装的 relay-git-guard.mjs 路径>` 作为普通用户运行。它只新建空的本地裸仓库和测试发布分支，输出身份和初始提交，不会接入产品部署、不打开监听端口，传入已存在目录会直接失败。

### 在构建中途交接（手机连接插件 0.7.16）

对能分段且可重复计算的脚本，可以同步**已经算出的内容**，不只同步命令行。两端必须持有相同的输入和构建代码；`recipeHash` 要包含代码、输入及影响结果的配置。会话、作业名和这个摘要共同确定一条进度记录。不把完整工作目录、环境变量或凭据写进记录。

- 普通 Node 构建可通过 `relay_environment` 返回的 `nodeModule` 导入 `ScriptProgress`。源端启动 `startProducer()`；把可恢复的中间结果交给 `save(previous, bytes)`。看到 `local` 只表示本机落盘，`waitPaired(checkpoint)` 成功才表示对端也已落盘。脚本结束时关闭心跳。每条记录最多 256 KiB；不是大文件备份。
- 备用端要先获准启动，再用 `waitForQuietReplica()` 等待。活着的慢步骤会持续发送心跳；传输中断后，备用端可从已确认的记录开始重算未确认的那部分。相同修订产生不同内容时停止，不任选其一。断网不等于断电，心跳超时也不是独占执行许可。
- 在不允许子进程访问进度库的 DSH 沙箱里，模型通过 `relay_script_checkpoint` 的 `load` / `quiet` 读取**本会话**的记录，把它交给脚本的 `computationSlice`。脚本返回新的数据，模型用 `save` 提交，仍须以对端确认区分本地与双端持久化。模型工具每条限 32 KiB，不接受命令或任选路径，不能在只读会话提交。

这不是跨系统搬运进程内存。未改造的程序、只留在源机器的输入，以及部署、付款、发布等对外操作，不能仅因心跳消失就重跑。此机制不自动启动未授权的备用进程。发布操作应走目标端回执核对。
Linux 沙箱可能看不到插件安装目录。请将包里的 `tools/computation-slice.mjs` 作为项目明确授权同步的构建输入，从项目内导入，不要为读取插件目录放宽沙箱。

### 0.7.17：跨系统交付项目目录和锁定的安装输入

先更新两端插件，再在原有的工作区输入清单中逐个写相对路径。例如：

```json
{"desktop:<原工作区 ID>":["package.json","package-lock.json","scripts/build.cjs","src/data/marker.json","vendor/packages/lib.tgz"]}
```

目录分隔符统一用 `/`。两端保留相同的相对路径；不接受目录通配符、上行路径、链接、设备名、隐私文件名、`node_modules` 或仅靠大小写区分的路径。最多 256 个文件、总计 8 MiB。此限额不是手机上传附件的限额。发起端只收集清单中的文件；接手端验证全部输入后才开始补文件，已有文件不同就保留原样并拒绝启动这次接力。只读会话、返回原有工作区时只做核对，不能补写缺失文件。文件很多或依赖含本机二进制时，仍需事先准备对应系统的检出和依赖。

`relay_environment` 的 `nodeSetup` 会区分依赖目录**不存在**和**已存在但未经验证**。只有检测到 npm、单一 npm 锁文件且没有 `node_modules` 时，才建议用当前主机的 `npm ci --ignore-scripts --no-audit --no-fund` 安装，再用 `npm ls --depth=0` 核对依赖。插件不自行启动安装，也不传输源机器的 `node_modules`。安装权限仍由原生 DSH 决定。不要为了修复半成品而覆盖其他任务正在使用的依赖目录。

断点验证使用 Windows 和阿里云 Linux 的两个隔离 DSH 实例、脚本化模型和本地 npm 包。先封存接力轮次，确认目标已持久保存整份输入，再在源端真正解包但尚未完成时终止 npm 并退出源 DSH。接手端仅使用此前收到的副本，重新做一遍本机离线安装、校验依赖并完成原会话的后续构建。不执行 `postinstall`，不把退出码当成发布回执。这个过程验证了**安装中断后任务仍能完成**，不是从解包到一半的内存位置恢复，也不覆盖未预交付输入的突然断电。

### 断电恢复后的构建产物（桌面插件 0.7.18）

例如，Windows 把一轮构建交给 Linux，云端完成后能将构建报告交回 **Windows 原工作区**。Windows 不需要启动 DSH，但要有网络且独立收件计划任务能以原用户身份运行。反方向也使用同一个收件协议。此处传送的是已完成的文件，不是运行进程的内存，也不是外部部署回执。

由**原工作区所属主机**在 `DSH_HOME/mobile-task-sync/relay-outputs.json` 指明允许回传的相对路径，不能用仓库中的文件自行授权。例如：

```json
{"desktop:<原生工作区 ID>":["reports/build.txt","artifacts/summary.json"]}
```

云端发起时用 `cloud:<原生工作区 ID>`。未配置时不回写原工作区；只读会话不签发回传授权。限 `reports/`、`artifacts/`、`dist/` 下的普通文件，支持文本、JSON、CSV、PDF、图片、Word、Excel 等指定后缀，每次最多 16 个、合计 4 MiB。只在对应的原生接力轮次成功结束、且文件集齐全时交付。接手的模型从 `relay_environment.resultDelivery` 读取暂存路径及清单；原会话下次调用 `relay_environment` 可在 `returnedFiles` 看到这轮的收件状态。

电脑长时间离线不会仅因时间过去而丢弃已封存的产物。原主机先持久保存文件与摘要，然后核对工作区身份并补写文件：同内容不重写、不同内容不覆盖。`delivered` 才表示成功写入工作区；`received` 只代表已落入收件箱；`unavailable` 表示轮次未正常完成或产物不齐/不合规；`conflict` 时保留远端副本，原文件不动。未确认的发件和待处理的本地文件各有 64 MiB 队列上限，满时不会驱逐更早的待交付内容。

在收件主机上，用安装包内的 `result_delivery.py status <收件箱目录> desktop` 查看明细；冲突文件可用 `result_delivery.py recover <收件箱目录> desktop <请求 ID> <新的恢复目录>` 导出到一个**尚不存在**的目录，核对后自行合并。Windows 用 `py -3.11` 运行脚本，Linux 用 `python3`，云端角色写 `cloud`。收件箱目录为 `DSH_HOME/mobile-task-sync`。

部署时先将 `result_delivery.py` 和 `project_inputs.py` 与云端 `task-transfer.py` 安装在同一只读程序目录，再更新 `task-transfer.py`；Windows 更新随包的独立收件程序。旧端不协商 `results-v1`，仍可同步原有会话，但不会交付新格式产物。

### 0.7.19：决定下一条普通终端命令在哪里启动

在原工作区的会话中打开「手机连接 → 本会话终端执行位置」，可以选「工作区默认」「本机」或「配对云服务器 / 配对电脑」。设置只属于这台主机的这个会话，重开 DSH 后仍有效，不会移走已运行的命令。无需给脚本加接力调用，也不需要预先列出每个命令名。若选择「工作区默认」，管理员仍可在工作区外的 `mobile-task-sync/relay-placement.json` 按原生工作区 ID 和命令全文指定位置，例如 `{"desktop:<工作区 ID>":{"pwsh":["npm run build"]}}`。默认不匹配时仍在本机执行；这不是安全沙箱。

适用范围是原工作区根目录的单个普通前台 `pwsh` / `bash` 调用。后台任务、交互式终端、并行工具调用和带额外执行选项的命令不支持此接力。源端通过正常审批后，在调用原生 shell **之前**封存上下文并结束本轮，不把一次未启动的命令伪装成执行成功。接手端仍通过 `relay_environment` 读取本机平台、工具、文件和原命令；它在原会话按本机权限运行合适的步骤。配置不自动传出整个目录或凭据，输入和结果仍用该工作区的清单。配对端不可达时可以排队；并不表示已开跑。不能在缺少接收确认时回退到源端再执行一遍。

接手端已开始构建时，源 DSH 退出不会杀掉配对端进程。回执只证明**这一条**被拦下的命令没有在源端启动，不证明更早的安装或部署没有生效。如果源端在接力包送达前突然掉电，或任意普通进程已经在掉电机器上运行，单靠此设置不能恢复该进程的内存、套接字或尚未落盘的数据。

可选的 Linux x64 PowerShell 运行时：从 PowerShell 官方 GitHub 发布页获取 `v7.6.10` 的 `powershell-7.6.10-linux-x64.tar.gz`，管理员运行 `sudo sh install-project-pwsh.sh /path/to/powershell-7.6.10-linux-x64.tar.gz`。安装器核对固定 SHA-256，用 `dsh-cloud` 账户测试后只链接到 `/opt/dsh-cloud/bin/pwsh`，不替换系统 Shell。Windows 专用模块仍不能在 Linux 上工作。

### 0.7.20：接手后核对原 GitHub 部署，不重复发布

`relay_deployment_ref` 在会话记录中保存要查的仓库、环境、提交和发布者，不创建部署。只使用用户已授权发布目标的真实信息，不从同名分支猜部署。已知 deployment ID 的情况下，接手端逐项核对仓库数字 ID、提交 SHA、环境、部署创建者、最新状态的发布者和部署 ID，然后报告 **GitHub 对该次部署的状态**。成功不是服务健康证明；`inactive` 也不是失败。网络错误、未授权、没有状态或身份不匹配统一保留为未确认，任何返回值都不授权重发。

普通终端可用 `relay_environment.deploymentVerification.helper` 给出的本机路径执行 `node HELPER TICKET`，`TICKET` 来自原生引用。助手只读固定 GitHub API，不读取部署日志或环境变量列表。私有项目可在运行助手的设备按需提供 `DSH_RELAY_GITHUB_READ_TOKEN`（仅部署读取权限）与 `DSH_RELAY_GITHUB_REPOSITORY_ID`（匹配才使用）；不通过手机、会话或接力包传令牌。如果创建部署的响应丢了，可在原有发布流程支持时提前把 `relay_deployment_ref` 产生的 `operation` 存进 GitHub 部署 `payload.dshRelayOperation`。查询在给定提交和环境下只接受唯一匹配；找不到、超过查询边界或有两次匹配均不重发。不支持这个标记且没有原 ID，就不能通过猜测补出回执。

**沙箱读不到插件目录或不能联网时**，无需放宽终端权限。管理员可以在接手端工作区以外的 `mobile-task-sync/deployment-watch.json` 设置最多八个精确的现有部署。例如（用真实值替换占位符）：

```json
[{"sessionId":"<原会话 ID>","target":{"repository":"owner/repo","repositoryId":"123","environment":"staging","sha":"<40 位完整提交 SHA>","deploymentActor":"456","statusActor":"789","deploymentId":"1001"}}]
```

只有清单内的目标由插件后台主动只读查询；来自聊天、脚本或模型的文字不能添加目标或触发主机网络请求。`relay_environment` 显示原会话中已记录引用的观察时间与结果；`relay_wait_deployment` 可等待首次观察或下一次状态变化。后台对运行中状态约每 5 分钟复查，已结束状态约每 30 分钟复查，并对限流退避；等待超时不等于失败。移除条目后工具不再返回它的状态。未接入的 CI、Shell 部署和任意外部业务仍需各自的目标回执，不能借用 GitHub 的成功状态。

### 不修改脚本的 Python 内存检查点（0.7.21）

适用于**预先用检查点执行器启动**的纯计算，不需要虚拟机，不会读取其他进程的内存。两个执行端需要相同的脚本、同版执行器和 CPython 3.11。执行器在语句、循环和函数调用的边界自动记录下一步的位置、调用栈、局部变量、循环游标和列表内容；若多个变量或调用帧引用同一列表，恢复后仍引用同一份数据。不使用 pickle，不从检查点加载 Python 代码。

1. 调用 `relay_environment`，从 `pythonCheckpoints` 读取此端 `checker`、`runner`、`ledgerRoot` 和本会话 ID。两端先用已授权同步的**原脚本**做预检：`python3.11 -IB "$CHECKER" check job.py --interval 512`（Windows 用 `py -3.11`）。两端的 `recipe` 必须相同；这也校验输入源码、执行器实现和间隔。预检通过不是容量或运行成功的保证。
2. 在备用端事先授权并启动 `python3.11 -IB "$RUNNER" standby job.py --session "$SESSION" --job my-build --root "$LEDGER" --interval 512`；在源端用 `primary` 代替 `standby`。作业名对同一会话同一次运算保持唯一；重跑新的作业应更换作业名。脚本不需要调用保存函数。两端仍按原有 DSH 会话权限启动命令；不能借此绕过只读模式或访问限制。
3. 源端在第一条语句前先等初始状态双端落盘；之后每批也必须得到对端确认才执行下一批。间隔可以从 1（每个控制步骤）到 65536，默认 512；按步数而非按毫秒计数。当单个原生运算很慢，恢复时该运算可能从头重算。未同步不报告为已保护；默认等待，`--timeout N` 可明确设定等待上限。
4. 只有预先启动的备用执行器才会在已配对检查点和生产端心跳均停止变化后继续（默认静默 12 秒）。它允许**纯计算**在原机离线时单机落盘；首次接管后的记录重新获得对端确认后恢复逐批等待。完成信息的 `restoredSteps`、`totalSteps`、`delivery` 区分起点、最终进度和实际副本数。`local` 不是双副本；恢复传输后原收件箱会补齐状态。断网不等于断电，不能据此为部署或付款取得执行权。

当前支持整数、布尔值、`None`、列表和列表别名，赋值、分支、普通位置参数函数（将调用结果赋给单一变量）、递归、`for ... in range`、`while`、`break/continue/else` 和最后的单参数 `print`。不接管已经在运行的解释器；不迁移线程、套接字、操作系统句柄、扩展模块、子进程。超出语法、调用深度（128 层）、单检查点（256 KiB）或现有收件箱容量时显式失败，不转而不受保护地运行。沙箱不能访问插件或账本时，可使用经授权进入项目的单文件 `python_state.py`；`slice` 从标准输入读取上一检查点的 Base64（第一次为空），输出 `recipe/state/done`，配合 `relay_script_checkpoint` 的 32 KiB 限制使用。此模式由调用方核实 `paired` 后才推进，不是后台自动热备。

### 0.7.22：实时源码版本、工具步骤和接力门槛

在专用工程的原生 DSH 会话发送 `/source-share --project`，可一次登记整个工程中符合范围的源码，之后新增的目录也会纳入。无需逐个文件配置。也可以在**原工作区**用 `/source-share src tests README.md` 登记要共享的顶层目录或文件；名字含空格时可用 JSON 数组。只有设备所有者能授权。在受信主机上也可以通过 `source_sync.py bind <mobile-task-sync目录> <工作区键> <原工程目录> src tests README.md` 登记。工作区键是 UTF-8 字符串 `desktop:<原工作区ID>` 或 `cloud:<原工作区ID>` 的 SHA-256。另一端只会自动绑定 DSH 为这个身份创建的工作区副本，远端不能指定本机路径。配置不在项目仓库内；不会因为打开桌面、个人目录或一整块磁盘就上传里面的文件。取消授权时，应先停止该工作区写入并在两端移除相应 `source-grants/<键>.json`；保留历史账本。

* 修改无需 Git 提交。保存的 UTF-8 源码、文档及配置按文件修订传输，支持创建、修改、删除。重命名表现为删除加创建，不同步文件权限、符号链接、隐藏目录、依赖、构建目录、明显的密钥文件名和仓库忽略项。普通源码本身可能含敏感信息，只授权可上传的源码目录。每个文件至多 2 MiB，每个工作区至多 4096 个文件、256 MiB；超限不报告就绪。
* DSH 工作时两端每约 1 秒检查已保存文件。原生工具执行前与返回后还会主动扫描，将会话、调用标识和执行边界对应到源码修订。原生事件触发增量历史发布。`returned` 表示调用返回，业务是否成功仍看原工具结果。监视器可捕捉已保存但尚未提交的改动，不承诺捕获两次扫描间被覆盖的所有中间字节或编辑器未保存的文字。
* 在已绑定的电脑工作区，工具启动前最多等 20 秒取得云端落盘回执；没有回执时不启动。执行后的确认超时仍保留真实工具结果，不冒充云端确认，也不重复执行。云端可独立记录后继续工作；电脑恢复连接后补传。桌面关闭时 Windows 独立收件任务按其原有频率运行，不是持续在线。源设备在第一份副本到达之前失去电源，远端只能使用已经确认的版本。
* `/source-share` 不带参数显示本机版本、对端持久接收进度、待合并文件。单向修改正常应用；有共同基线的非重叠文本修改可自动三方合并。重叠编辑、删除对修改、无共有基线的不同内容保留分支，不写冲突标记或用时间戳覆盖。已共享源码的原生接力必须带发送方日志版本；接收方未持久收到指定版本、有冲突或未应用时，不启动下一轮。此机制不把未完成的 shell 输出当成执行完毕，也不触发任意副作用的重试。
* 用 `source_sync.py export <账本目录> <工作区键> src/example.ts <新目录>` 取出各版本及其修订 ID；手工合并到工作区后，用 `resolve <账本目录> <工作区键> src/example.ts <当前全部修订ID...>` 登记合并结果。工具不会选择哪一份应被丢弃。SQLite 满、无法读取文件、Git 忽略规则或文件夹绑定失效时应先处理错误，不要删除账本或假装已同步。

部署时将 `source_sync.py`、`source_exchange.py`、同版 `project_inputs.py` 放在两端 `transfer.py` 旁边，升级配对的插件和 Windows 独立收件任务。传输使用现有校验主机密钥的 SSH，协商 `sources-v1`；旧端不能收到新格式的源码接力。文件追踪不改变手机 IPA，也不打开额外监听端口。
